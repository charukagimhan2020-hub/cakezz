# What to say if asked (viva)

**Why one process instead of four services?** The four components are four folders with their own tests and README, so each member owns and can explain one part. At runtime c1 imports c2, c3 and c4 as normal Python modules, so there is one Flask process. Reason: Render's free plan puts every service to sleep after 15 minutes. A chain of four sleeping services would have to wake one after another and the shop would time out. One process wakes once, and a function call between components costs microseconds instead of a network request that can fail.

**Why does the shop forward the raw browser values?** The attacks work by changing what the browser sends: unit price, quantity, discount, total. If the shop "fixed" the numbers before asking RuleLock, RuleLock could never see the tampering. So the shop stores and forwards exactly what it received, and RuleLock compares it with the truth it reads itself from the database (catalog prices, coupon table, order history). The server never trusts the browser, and neither does RuleLock.

**Why `reject` and not a fourth action name for the rate limit?** The shop can only do four things with an order: continue (`accept`), continue without the discount (`void_discount`), keep it for review (`hold`), or stop it (`reject`). Those four decisions map one to one to the payment action. A rate limit is not a different outcome for the order, it is a side effect on the account, so it travels in a separate field (`account_action`: rate_limit, 30 minutes). Likewise `hold_cod_order` and `hold_order` are only the name of the action taken; the decision is `hold`. This keeps the contract between the shop and RuleLock small and stable.

**How could a store owner plug in their own shop later?** Three steps, no changes to RuleLock's logic. (1) Insert the order first so it has a stable number. (2) Send shopper events to `POST /events` (login, browse, add to cart, apply coupon, checkout) with a session id, a device id and hashed phone and address. (3) Before taking payment, call `POST /review-order` with the order as submitted and a Bearer token, and act on the answer (`decision`, `payment_action`, `customer_message`). RuleLock needs read access to the shop's catalog, coupon table and order history; in this project that is `c1-data-collection/db.py`, the one file to adapt to another database. The same HTTP contract works from PHP, Node or Python.

**Why a rule engine and an anomaly model?** Rules catch what we know is wrong (three coupons, a price that is not the catalog price): they are exact, explainable and never wrong about the cases they cover. They cannot catch behaviour that breaks no single rule, for example one device logging in to four accounts. The Isolation Forest is trained only on normal sessions and scores how far a new session is from them, so it can flag the unknown. Rules decide first; the model only has a say when the rules pass.

**Why Isolation Forest?** It needs no labelled attack data (we have none), it is fast, and it is easy to explain: unusual points are isolated with fewer random splits. The four features are simple counts a shop can compute from its own logs.

**Is the model good?** Honestly: it is trained on synthetic data and evaluated on synthetic abuse that we generated with the same assumptions, so the evaluation is circular. It proves the pipeline works, not that it would catch real fraud. To get real numbers we would need real shop traffic with labelled abuse. We also chose a sensitive setting: all demo abuse is flagged, but about 8% of the broad normal mix is held, mostly sessions with two accounts on one device. That trade-off is documented in `rulelock/c3-anomaly-detection/README.md`.

**What happens when something fails?** Fail safe. Every pipeline step is wrapped; if one fails the order is held (a rule reject stays a reject), never accepted. If RuleLock is asleep or down, the shop waits up to 60 seconds and then holds the order. If the order cannot be changed or the review cannot be stored, the answer is hold.

**Why is the audit log insert-only and minimal?** An audit log you can edit is not evidence. A database trigger rejects updates and deletes, and each review plus its audit row is written in one transaction. The row has no name, phone, address or raw request, only what is needed to explain the decision. Reviews are idempotent per order: sending the same order twice returns the stored answer and does not enforce twice.

**Why does the monitor go through a PHP proxy?** The RuleLock token must never reach a browser. The monitor page calls `api.php` on the shop (admin session only), and the server adds the Bearer token.

**What is deliberately vulnerable, and is that safe?** With the toggle OFF the shop trusts prices, quantities, discounts and coupons from the browser, and has no COD checks. It is a lab on our own accounts, with a banner on every page, and it must never hold real customer data or real card numbers (the fake payment page never reads or stores card input).

**What would you do next?** Real traffic and labels, a proper evaluation (precision and recall on real abuse), more features (for example address and phone reuse over time), a review queue for held orders, per-shop settings, and signed requests between the shop and RuleLock.
